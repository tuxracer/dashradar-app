# dashradar

A single-screen web app that turns a dash-mounted phone into a live, on-device police-vehicle detector, presented as a full-screen radar-detector-style signal meter. Real-time object detection runs on the rear camera feed, which is never shown on screen; only the meter and, during a detection, a small evidence card are visible. Client-only **Vite React SPA**, **offline-first PWA**, **no backend, no accounts, no data leaves the device**.

**This is a computer-vision detector, NOT a radar detector.** It cannot detect radar, LIDAR, or any RF emission; "radar" is only a visual metaphor for the UI. In user-facing copy (README, marketing, in-app strings), never call the app a "radar detector" or say it detects radar. The correct framing: an on-device, computer-vision police detector that spots patrol vehicles on the road in real time.

[docs/TRD.md](docs/TRD.md) is the full technical reference (architecture internals, worker protocol, settings, detection domain, offline strategy, error handling). This file holds the conventions and the gotchas that must not regress.

**Repository URL**: https://github.com/tuxracer/dashradar-app

## Design & Use Case

Primary use case: **landscape, on a dash mount**. The driver interacts by reaching across the cabin at arm's length and glancing briefly. Rules that follow:

- **Beautiful minimalism.** Show only what earns its place; high contrast, no clutter.
- **Large touch targets.** Every control must be hittable on the first try, one-handed, without looking closely. When in doubt, make it bigger.
- **Glanceable, low-effort interaction.** Few taps, obvious state, no fine motor precision.
- **Landscape-first layout.** Portrait must not look broken. The one exception is the first-open intro (`IntroScreen`/`IntroScene`), composed portrait-first because a first-time user meets it holding the phone in the hand.
- **Interactions animate; idle screens do not.** A state change someone caused should be shown happening: what arrived, what left, and where a selection went. Reuse the vocabulary in `src/globals.css` (`rise-in`, `swap-in`, `row-out`, all on one easing curve) instead of adding a curve per component, stagger a list in rather than popping it in whole, animate a row out rather than letting the rows below it jump into the gap, and pair every animation with its `motion-reduce:` variant. The bar is whether the motion carries information: the model screen's amber selection wipe says which of two near-identical rows took the selection, while a spinner during a download says nothing the percentage does not. Keep every one of them one-shot and triggered by a tap, which is what makes them compatible with the budget below.
- **The QR code complements a share action; it is never a fallback for one.** Wherever the app hands itself to another device, show `ShareQr` unconditionally and add the Web Share button on top where `canShareApp()` is true. Never gate the QR on the share sheet being missing. The two solve different problems: the QR moves the app to a *second screen* someone is holding (and needs nothing from the browser), while the share sheet moves it to a *second device* of your own, which is the only thing that helps when the failing device is the phone in your hand. Treating either as the other's last resort removes a route that was doing its own job. Same rule for any future handoff surface, not just `IntroScreen` and `UnsupportedScreen`.

**Thermal and battery budget is a first-class constraint.** Continuous neural inference on a phone clamped to a windshield in direct sun is close to the worst thermal environment a phone sees, and a detector that throttles or kills the phone mid-drive fails silently exactly when the driver relies on it. The current balance is the 1 s scan floor (`MIN_FRAME_INTERVAL_MS`) plus a rest that grows superlinearly with the round trip and is capped by `MAX_FRAME_INTERVAL_MS`, with the coasting tracker and peak-hold meter covering the gaps between results. Gate any change that runs inference more often or more heavily on "does this heat the phone or drain the battery on a real dash-mounted device in the sun", verified on-device, and bias toward the conservative side.

**Reason about heat as the share of time the GPU is busy, not the idle between runs.** These come apart, and the difference already shipped as a bug: resting a fixed multiple of the round trip looks adaptive and gives a throttling phone visibly longer breaks, while holding its duty cycle pinned at exactly 50% however hot it gets, so the pacing never backed off the load that caused the throttling. Any rule stated as a multiple of how long the work took holds the ratio constant by construction, and the mirror image is just as wrong: a rule stated as a fixed number of milliseconds lets the busy fraction climb with the round trip, so it backs off hardest on the device that needed it least. Rest ratios are the well-formed lever, because a ratio of r is exactly a ceiling of 1/(1+r) on the busy fraction everywhere it binds. Check what a proposed pacing rule does to the busy fraction across the whole round-trip range, not at one comfortable value.

**The budget covers always-on UI work, not just inference.** Sessions run for hours and idle scanning is the dominant state, so "cheap" per-frame work compounds: a rAF loop or timer that runs for the whole session must park itself once its output is a fixed point and be woken by change (see the `RadarDetectorScreen` meter loop), and per-tick DOM writes must be skipped while the values behind them are unchanged. Don't add unconditionally scheduled per-frame loops, polling timers, or always-on CSS animations without weighing their idle-state cost; CSS animations run on the compositor but still keep the display refreshing.

### Rejected ideas (do not re-propose)

Ideas evaluated in feature brainstorms and rejected. Don't bring these up again:

- **Detecting red/blue flashing emergency lights** (strobe/flicker detection, "active lights" alerts, reflected-strobe or cloud-bounce detection, or anything similar). A vehicle running its emergency lights is already the most visually obvious thing on the road; the driver needs no help noticing it, so the feature adds cost without value.
- **Windshield-reflection HUD mode** (mirroring the display so it reflects off the windshield). The phone is also the camera: laying it face-up on the dash to project the UI points the camera at the ceiling, so the detector stops working the moment the mode is used.
- **Proactive thermal backoff driven by the Compute Pressure API** (`PressureObserver` as another engine input, raising the rest ratio at `serious`). The gap it aims at is real: a phone that is hot but not yet throttled still turns in a healthy round trip, which is the busiest point on the whole duty-cycle curve, and a ramp keyed on round trip cannot see it. No target device has the API, though. Chrome for Android and Android WebView do not implement it, deprioritized because the OS telemetry it needs became unreachable after Android 11, and WebKit has nothing; desktop Chrome is the only place it fires, and there scanning is an escape hatch behind a confirm on the QR handoff. Revisit only if Chrome for Android ships it.

## Architecture

Client-only **Vite 8 React SPA** with no server runtime (the build is a static `dist/`). Data flow: `src/App` → `DetectionProvider` (consumed via `useDetection()`) → `src/workers/detection` (RF-DETR ONNX on raw onnxruntime-web in a Web Worker, WebGPU only) → `src/lib/detection` class enrichment plus confidence filter → `src/lib/detectionTracker` coasting smoother → `src/lib/detection` HUD shaping (all pure, no React). `src/lib/detectionEngine` owns the worker lifecycle and frame pump, framework-free; `DetectionContext` is a thin `useSyncExternalStore` adapter over it, and components only ever read `useDetection()`.

Module map (internals in the TRD's Architecture and Detection domain sections):

- `src/context/DetectionContext/`: thin React adapter over the detection engine; mirrors engine snapshots via `useSyncExternalStore` and pushes inputs (video, visibility, settings) in.
- `src/lib/detectionEngine/`: the framework-free worker lifecycle and frame-pump state machine; pacing, periodic worker recycle, derived running state, crash-sentinel heartbeat, contact state, pull-based debug snapshot. Built on rxjs internally (see the `writing-rx-streams` skill); its snapshot/subscribe interface is the seam React sits behind.
- `src/context/SettingsContext/`: localStorage-backed settings (`settings`) behind the `developerOptions` master switch. The provider hands out already-gated effective values, so consumers never repeat the gate. Every developer option starts at its `DEVELOPER_OPTIONS_OFF` value, so turning the master switch on reveals rows without turning anything on; a `settingsVersion` migration clears the ones that used to default on. The model selection (`modelIds`) is a developer option too, and the only one that commits through `commitModelIds`, which confirms the `localStorage` write landed, because its caller reloads the page on the next line and must not reload into the selection it just left.
- `src/context/VideoSourceContext/`: which video file, if any, the detector scans instead of the camera, plus the object-URL lifecycle. Both ways to set a source are developer options, and it sits inside `DetectionProvider` because every swap detaches the engine's video before the element it was capturing from unmounts. It mints a `feedId` per swap, which is how a consumer tells the two camera sessions either side of a clip apart; both have a null source, so a camera failure recorded before a clip would otherwise come back with the error screen instead of the camera being asked again.
- `src/workers/detection/`: downloads the ONNX weights, runs inference; pure preprocess/decode in `inference.ts`, constants in `consts.ts`, typed message protocol in `types.ts`.
- `src/lib/`: React-free domain modules, one directory each.
- `src/components/`: `CameraView` (hidden `<video>`, the feed is never shown outside the developer-only detection view below), `RadarDetectorScreen` (the driver-facing detection UI; rAF peak-hold loop writing straight to the DOM, drives the beeper and contact card), `SceneView` (the second driver-facing view: react-three-fiber 3D scene placing `scan.tracks` on a ground grid via `src/lib/scenePlacement`'s pinhole math; demand frameloop, owns its own beeper, falls back to the radar view on render failure), `DetectionView` (developer-only alternative that shows the feed and draws the model's boxes over it), `StatusBar` + indicator pills plus `ViewModeButton` (the radar/scene toggle, the persisted `viewMode` setting's only control, hidden while the detection view overrides both), `SettingsScreen`, `ModelScreen` (developer-only picker for the checkpoint, opened from settings; registers models pasted as Hugging Face URLs via a trial load, confirms, commits the selection, and reloads to apply it), `DebugOverlay`, `VideoDropTarget` + `VideoFileView` (the video-file feed: a window-wide subscription to `src/lib/videoFileDrop` and the player that runs a clip through `src/lib/videoFileFeed`, standing in for `CameraView` whenever a source is set; a clip outranks the intro, the permission ask, and the camera error screens on purpose, since a machine with no camera or a denied one is where it earns its keep. Both the drop and the settings row that clears it are behind developer options, and switching them off returns a running clip to the camera; the drop is still cancelled while they are off, since refusing the drag navigates the browser to the file and ends the session), `ShareTarget` (the handoff cluster: SCAN TO OPEN annunciator, QR in lock-on brackets, Web Share button; shared by the desktop intro and `UnsupportedScreen` so the app's two handoffs cannot drift apart), `UnsupportedScreen` (the WEBGPU_UNSUPPORTED handoff, framed as an invitation rather than an error), intro/permission/load/error screens.
- `src/types/`: shared detection types and guards.

**Scene-change gate**: before preprocessing, the worker reduces the frame it is about to scan to a grid of per-tile mean lumas and compares it against the last frame it actually scanned; a frame that has not moved gets `scan-skipped` instead of an inference. Two properties are load-bearing and easy to break. The statistic is the largest single tile's change with the frame-wide shift subtracted, never an average: a distant patrol car covers a few dozen of 262,144 pixels, so a frame-wide average cannot separate it from noise, and subtracting the shift is what keeps an auto-exposure correction from reading as movement. The baseline is the last frame *scanned*, so drift accumulates until something crosses the line rather than resetting each frame. A skip touches no published detection state, because a scene that did not change cannot have lost what the last scan found; never express one as an empty `detections` result, which would coast the tracker toward dropping the vehicle and decay the meter behind it. The one thing a skip does publish is the `scanCompletedAt` heartbeat the radar sweep runs on, because a gated session holding a still scene is scanning perfectly well and must not look frozen. `SCENE_GATE_MAX_SKIP_MS` forces a scan regardless and is not optional: a threshold set above what a distant vehicle produces and a camera feed that has frozen are both indistinguishable from a still scene from inside the app, and either one without the bound is the failure this project already refused in the wasm fallback, a detector that never scans while looking like it works.

**Frame pump**: only one frame is ever in flight (latest wins, no queue). Captures are at least `MIN_FRAME_INTERVAL_MS` (1000 ms) apart, and every capture additionally rests a multiple of the last round trip: `PACING_REST_RATIO` (1) until the round trip passes `PACING_REST_RAMP_MS`, then climbing with it to `PACING_REST_RATIO_MAX` (3), so a slowing device's GPU duty cycle falls from 50% toward 25% instead of holding. `MAX_FRAME_INTERVAL_MS` (5 s) caps the result. The dev-only `throttleInference` off state drops the delay to 0; turning Developer options off always restores the floor. The pump pauses when the page goes hidden and while settings are open, each pauser resuming only sessions it paused. Workers are recycled every `WORKER_RECYCLE_AFTER_MS` (15 min) at a result boundary to bound native memory growth; one-time analytics events are ref-gated so recycles never re-fire them. A worker that leaves a posted frame unanswered for `WORKER_REPLY_TIMEOUT_MS` (30 s) is treated as wedged and recycled, since a hang fires neither a worker-error message nor `onerror`; a session that goes silent for `WORKER_LOAD_TIMEOUT_MS` before reporting ready is recycled the same way (an inactivity bound, so a slow download posting progress never trips it).

**Rendering**: pure client-side SPA. Never introduce SSR/SSG.

**Bundling**: ship all application code in the initial load; no lazy loading, dynamic `import()`, or code splitting (runtime chunk fetches break offline use). The one sanctioned exception is the detection worker chunk, which the Workbox precache includes.

**Telemetry**: Vercel Analytics and Sentry are both gated on Do Not Track / Global Privacy Control via the [`privacy-signals`](https://github.com/tuxracer/privacy-signals) package (extracted from this repo; only `isTrackingOptedOut() === false` enables them, since `null` means the signals were unreadable and is not consent), and dev builds emit nothing.

## Git Workflow

- **Always rebase when integrating to `main`, never create merge commits** (`git rebase`, `git merge --ff-only`). Keep history linear.
- **Already on `main` and asked to commit? Commit straight to `main`.** Don't create a branch first. Branching only to fast-forward `main` right back is a pointless round trip: the commit lands in the same place, just after two extra steps and a deleted branch. Branch only when there's a real reason (asked for, work already on one, or genuine isolation for a long or risky change); a big diff is not a reason on its own.
- **Commit finished work in the turn that finishes it, without asking.** When a requested change is done, verified (`pnpm check` and `pnpm test` green), and forms an atomic unit, commit it and report what was committed. Never close a turn with "nothing is committed, want me to commit?" or any variant: that question is always the wrong move here. A local commit is trivially revertible, so an unwanted one costs one `git revert`, while asking costs a round trip every single time. Split the work into atomic commits where it genuinely covers separate concerns.
- **Never push, and never ask about pushing.** Pushing to the remote is always manual. Don't offer it, don't raise it as a next step, don't ask for permission to do it; the local commit is where the work stops.
- **Keep commit messages short.** A subject line, and a body only when the diff leaves a real question unanswered: why this and not the obvious alternative, or what breaks if someone reverts it. Two or three sentences is a normal body and most commits need none. Don't restate what the diff already shows, don't list the files touched, don't explain the reasoning in paragraphs, and don't argue the change's merits. The reader is scanning `git log` to find something, not reading an essay.

## Model

A custom **RF-DETR Nano** checkpoint fine-tuned on Las Vegas Metro police vehicles, published at [`tuxracer/las-vegas-metro-rfdetr-nano`](https://huggingface.co/tuxracer/las-vegas-metro-rfdetr-nano) and trained/exported from the sibling repo `~/Development/las-vegas-metro-rfdetr-nano`. Mobile WebGPU is the only target and the only execution path, so a bad export has nothing to catch it. `src/lib/detectionModels` defines the uniform entry shape and the registry the developer model picker adds to; the `shipping-a-model` skill holds the mechanics.

Everything about the head is read from the weights at load. The width comes off the `labels` output of the run the worker already performs, and the classes come from the `names` map the export stamps into the ONNX metadata (`classesFromMetadata`, read by `src/lib/onnxMetadata`): a map of logit index to label, which becomes the label a box carries. The HUD draws that label as-is and gets its uppercase register from CSS, so no derived copy of the string exists to drift from it. Labels and the logits they index therefore come from one file and cannot disagree, which is why nothing is declared here for a mismatch to be caught against. A file that names nothing still loads and detects, with generic per-slot labels, because the meter reads scores rather than words. The table stays in the worker, the only place a logit index means anything.

There is no allowlist: every class a checkpoint names is decoded and shown. That does not make a new class free. `hudSignal` takes the max score across every detection regardless of class, so a new class immediately drives the dial, the `ALERT_THRESHOLD` ring, and the beeper, with no per-class alert concept to opt it out (a `person` class, for instance, would beep and flash red at every pedestrian). [docs/Models.md](docs/Models.md) is the contract a checkpoint has to meet to run here (tensor signature, head layout, precision, how to register it), and is where to send anyone asking what it would take to add a model. Read the `shipping-a-model` skill before changing the checkpoint, the export, the signature, or the revision.

**`CONFIDENCE_THRESHOLD` belongs to the checkpoint, not to the app.** Every release recalibrates its own score distribution and publishes the operating point it measured precision and recall at, so a checkpoint swap means reading the new release's recommended threshold and moving the constant with it; carrying the old number across leaves the detector quietly deaf or quietly noisy. Round it to the nearest tenth, because the developer confidence slider moves in tenths and a floor off that grid cannot be dialed back to by hand, which would also let turning Developer options on shift the threshold.

## Gotchas

- **WebGPU is the only execution path; don't reintroduce a CPU (wasm) fallback.** The int8 build that used to serve it measured >10 s round trips on an Android phone where WebGPU takes ~500 ms. Scanning the road once every ten seconds misses most of what the car drives past, so shipping it as a silent fallback made the app look functional while being useless, which is worse for the project than not running. A device that fails `probeWebGpu()` (which gates on the `shader-f16` feature the fp16 model needs, plus actually acquiring an adapter and device) gets the terminal `WEBGPU_UNSUPPORTED` screen instead, after the intro, before the camera ask, and before any model bytes are fetched.
- **Raw onnxruntime-web on purpose, never the Transformers.js `pipeline()`.** The head is a sigmoid scored per class, with an unused background slot at index 0 and a width measured off the loaded session, and the pipeline's softmax-with-background DETR decode drops every real detection.
- **The worker imports `onnxruntime-web/webgpu` (native C++ WebGPU EP), and that import is load-bearing.** Graph capture (`WEBGPU_GRAPH_CAPTURE`, on) requires it: the root import's JSEP kernel registry has no TopK, so this graph's TopK node lands on CPU and capture fails deterministically. `ORT_RUNTIME_FILES` in `vite.config.ts` must track the import (asyncify files for `/webgpu`). Keep the fallback to a plain WebGPU session. WebKit skips the capture attempt entirely (`isWebKitUa` in `src/lib/browserEngine`), on measured cost/benefit rather than crash attribution: on an iPhone 16e capture bought no round-trip improvement, so it has no upside there to weigh against instability, while on Chromium Android the win is large. Don't justify the exclusion with crash telemetry. DASHRADAR-2's iOS crashes never correlated with capture: nine of ten had it off, all inside the first ~21 s of scanning. Don't lift it without a measured WebKit round-trip win either. Pre-switch JSEP op behavior does not transfer to the native EP; re-check before relying on it.
- **Frame-pump invariants in `src/lib/detectionEngine` are structural, keep them that way**: one frame in flight comes from the pump being a sequential rxjs loop (capture, post, await result, pace, repeat), stale-capture invalidation comes from teardown-by-unsubscription, and never handing a frame to a still-loading worker comes from each session's pump starting behind its `loaded$` (set once the worker's "ready" message arrives). The two deliberate exceptions are `awaitingResult`, a session-scoped flag that lets a stop/start crossing an outstanding reply resume correctly (a case pure subscription scoping can't express), and its data companion `postedFrame`, the engine-scoped record carrying the in-flight frame's geometry and timings, which the result handler reads because worker replies don't echo the frame they answer. Don't add other imperative state (flags, counters, shared timers) alongside the streams; if a change can't be expressed by scoping work under the right subscription, rethink it. The engine's running state is derived from its inputs (video attached, page visible, settings closed), never commanded. Unsolicited worker results are processed on purpose (the handler, not the pump, owns result processing).
- **jsdom can't run the worker, inference, or the camera**, so green tests say nothing about whether detection works. Tests inject a fake worker through `DetectionProvider`'s `createWorker` seam and stub `createImageBitmap`/`getUserMedia`; the pure `preprocess`/`decodeDetections` helpers are unit-tested directly. Real verification is the `verifying-in-browser` skill.
- **Reaching the real camera during browser verification is expected here, not an incident.** Analyzing the live camera feed is this app's entire purpose, so a verification session that activates the actual webcam, or captures a frame with a person in it, is in-scope and needs no escalation or apology. Prefer a mocked canvas stream when the camera itself is not what's being verified, and don't retain captured frames beyond the check, but treat contact with the real camera as normal operation of the thing being tested.
- **Model caching pins a revision.** The `"model-cache"` Workbox route is `CacheFirst` keyed on URL, so a model's weights URL pins its registry entry's `revision`, never `main`; the `shipping-a-model` skill has the release runbook. The ORT runtime is served same-origin from `/ort/` by the `ortRuntime` Vite plugin and cached by the `"ort-runtime"` route; both routes are excluded from the precache glob.
- **First-visit model caching requires waiting for service-worker control.** The engine defers the worker's `load` until `navigator.serviceWorker.controller` is set (production only; `waitForServiceWorkerControl`, bounded by `SW_CONTROL_TIMEOUT_MS`). Don't move the model fetch back to fire unconditionally on mount. Dev has no service worker at all, so `cacheModelInDev` covers dev instead.
- **Cross-origin isolation (COOP `same-origin` + COEP `require-corp`) is load-bearing.** Headers come from `vercel.json` (prod) and Vite config (dev); they enable `SharedArrayBuffer` and multi-threaded WASM. Inference runs on the GPU, but onnxruntime-web's runtime is itself a wasm module hosting the WebGPU EP and running any node it can't take, so the threading still matters. Don't add a cross-origin `<script>`/`<link>`/no-cors fetch without CORS/CORP or it will be blocked.
- **Never upscale frames fed to the model.** Every crop drawn onto the 512x512 input must come from at least 512x512 native camera pixels. This is why `CAMERA_CONSTRAINTS` requests ~1024 per axis (the 2x crop lands at 512 native) and why zoom stops at 2x. Gate any new zoom level or capture-size change on the granted stream's actual dimensions (`min(videoWidth, videoHeight) >= zoom * INPUT_SIZE`), never fall back to upscaling.
- **`mapBoxToViewport` assumes `object-fit: contain`** on the video element. The detection view draws its boxes through it, so the mapping and the video's CSS have to change together: if the feed stops being rendered `contain`, every box lands in the wrong place. Fitting is deliberate there: under `cover` the parts of the frame the viewport crops away take their boxes with them, and the whole point of the view is seeing everything the model was handed.
- **Worker module import exception**: never import `src/workers/detection/index.ts` (it pulls onnxruntime-web into the importer). Consumers import protocol types and guards from `@/workers/detection/types`, constants from `@/workers/detection/consts`, and the pure geometry helpers from `@/workers/detection/inference`, all directly. This is a deliberate exception to the import-from-module-index rule; `inference.ts` in particular has to stay free of onnxruntime imports, since the engine reads `centerCropRegion` out of it so the pre-cropped capture and the worker's box mapping cannot disagree.
- **The r3f `Canvas` cannot mount in jsdom** (no WebGL, no ResizeObserver), so `SceneView` probes for a WebGL2 context before rendering it and falls back to `onRenderFailure` plus `null`. That probe is the testing seam: never render a `Canvas` unconditionally, and keep App-level tests asserting the degrade-to-radar path rather than trying to mount the scene.
- **`SceneView` must stay `frameloop="demand"` with invalidation only while an animation is unfinished.** The glyph animator invalidates once per scan and then only while a tween or fade is mid-flight, so a static scene renders zero frames; that is the thermal budget applied to a 3D view that is on screen for whole drives. Never switch it to `frameloop="always"`, add an unconditional `invalidate()`, or attach a per-frame `useFrame` effect that does not gate its own re-invalidation. The beeper's driver loop parks on silence for the same reason.
- **Sentry's react component annotation must stay off; it breaks the scene view in deployed builds only.** The annotation stamps `data-sentry-*` attributes on JSX elements, r3f reads dashed props as nested object paths (the `material-opacity` mechanism), and an annotated element inside the Canvas throws at mount, leaving the scene black. `ignoredComponents` does not help (it suppresses only root annotations; nested elements keep theirs). The trap is that the plugin only runs when `SENTRY_AUTH_TOKEN` is set, so local builds look fine while every Vercel build is broken; test that class of change with `SENTRY_AUTH_TOKEN=dummy pnpm build` and a served `dist/`.
- **three ships whole once r3f is in the tree.** Fiber's JSX catalogue registers the entire three namespace, so named imports do not shrink it; wiring `SceneView` into `App` grew the initial chunk from 147 to 385 kB gzipped, an accepted cost. Don't promise import discipline will reduce it, and don't add three-adjacent packages (drei and friends) without checking for duplicate-three hazards and weighing the same bundle math.
- **vitest transpiles without typechecking, so run `pnpm check` before debugging a baffling test failure.** Importing a name a module doesn't export yields `undefined` at runtime, not an error, and the symptom lands far from the cause: `vi.advanceTimersByTimeAsync(undefined)` advances nothing and makes a correct implementation look broken, which once cost an hour of stream debugging that tsc would have flagged instantly. The usual source here is `src/context/DetectionContext/consts.ts`, an explicit named re-export list: a new `detectionEngine` constant must be added to it before tests can import it from `@/context/DetectionContext`.

## Coding Standards

- **Never log sensitive data** (API keys, tokens, passwords); use `[REDACTED]` if a value's existence matters.
- **No a11y lint**: jsx-a11y is intentionally absent; don't add ARIA markup purely for convention or flag missing aria tags in reviews.
- **No em dashes or AI-isms in docs**: plain, direct voice; no "delve", "seamless", "robust", "leverage", adjective triads, emoji headings, or "In summary" wrap-ups.
- **Package manager**: `pnpm` for everything.
- **ESM imports only**: `import`, never `require()`.
- **Arrow functions**: `const foo = () => { ... }`. Convention only, no lint rule catches it.
- **Reserve the `use` prefix for React hooks**: boolean options are `systemFont`/`enableCache`, not `useSystemFont`.
- **Named imports**: `import { pipe, filter } from "remeda"`, never `import * as R` (tree-shaking).
- **Import paths**: cross-module imports use the `@/` alias; relative paths only within a module. Import from the module, not internal files (`@/lib/detection`, not `@/lib/detection/consts`), with `src/workers/detection` as the one exception above.
- **Module structure**: modules are directories named after their primary export, containing `index.ts` plus optional `consts.ts` (every exported constant lives here, never in `index.ts`), `types.ts` (types and guards), and `tests.ts` (`.tsx` when tests render JSX). `index.ts` re-exports types and consts. No barrel-only files. This holds for `src/App` too, and there are no `*.test.ts`/`*.spec.ts` files anywhere: vitest's `include` is narrowed to `**/tests.[jt]s?(x)` so an off-convention filename simply never runs, rather than passing green and going unnoticed.
- **React context over prop drilling** for app-wide state (see `DetectionContext`).
- **Remeda utilities** over manual loops where readability wins.
- **Named constants**, no magic numbers; underscore separators for numbers 1000 and up (`1_500`).
- **Local dates, not UTC**: never `toISOString()` for a date-only value; use local getters.
- **DRY**: extract a helper once a pattern appears 3+ times; shared utilities go in `src/utils/` (create it on first need, module-directory convention).
- **JSDoc**: skip `@param`/`@returns`; types cover them.
- **Loading indicators**: delay ~1 second to avoid flash.
- **Settings row descriptions**: exactly one short sentence that fits on one mobile line; no clause chaining, never spell out on/off states or write "when on"/"when off".
- **Intl API** over manual date/number formatting.
- **Branch on source values, not derived ones**: read the condition off the value that decides it, not off an intermediate boolean someone set earlier.
- **Type guards over `as` assertions** on runtime-unknown values: use remeda guards or write one. Union-type guards validate the actual allowed values and use the named type in the return annotation (`value is DetectionErrorCode`), not a hardcoded union.
- **Typed errors over string messages**: custom error classes with a typed `code` plus an `isXError` guard (see `CameraError` in `src/lib/camera/types.ts`).
- **Every `await` is a teardown window: re-check before committing the result.** Anything can change while an async acquisition is pending, including the caller deciding it no longer wants the result. After the await, re-validate the state that justified starting (a cancelled flag, the acquired flag, the live subscription) before storing the result or firing a side effect, and dispose the fresh resource when the answer is no. This matters most for resources that outlive the function when leaked: wake locks, media streams, ImageBitmaps, workers. The wake-lock manager once stored a sentinel granted after release() had already run, keeping the screen awake after scanning stopped; the `acquired` re-check in `src/lib/wakeLock`, the `cancelled` flag in `src/lib/camera`'s feed, and `captureFrame`'s teardown flag in the detection engine are the pattern to copy.
- **ImageBitmaps are manual memory.** GC does not reclaim their backing store promptly, sessions run for hours, and a leak per frame is a crash per drive. Every bitmap has exactly one owner responsible for `close()`, and every handoff moves that ownership explicitly: the pump transfers the frame to the worker, `swapContact` is the single close site for the published contact's crop, and a capture resolving after teardown closes itself. Never add a second site that closes "the previous" instance of the same bitmap; route it through the one owner.
- **Watch a new regression test fail before trusting it.** A test written alongside a fix must be run against the unfixed code (stash the fix) and fail there for the stated reason; a test that never failed may pass for reasons unrelated to what it claims to guard, and a test that fails for the wrong reason is hiding a bug of its own. Read the failure, never just the count: `toMatchObject({ key: undefined })` fails when the key is merely absent, so it reports a passing assertion about a value as a failing one about key presence. A new branch also earns guard tests that cannot fail against the old code, because they guard against the branch being taken too widely and there was no branch before; say which tests those are rather than implying the whole set failed.
- **Tests verify behavior, not implementation**: never assert a constant's value; test the behavior the constant affects.
- **Test logic that can break, not values that were typed in.** A test that asserts a function returns a specific UI string is a change-detector: it can only fail when someone intentionally edits the copy, and then the "fix" is to paste the new string into the test. It proves nothing and adds friction to every copy change.
- **Hold a high bar for what earns a unit test.** Coverage for its own sake is not a goal; a test per line of code is noise that slows every future change. Write tests for the things that can break without anyone meaning to: state machines and race-prone lifecycles (the frame pump, worker recycling), math and decode logic, filtering and threshold rules, parsers and type guards, and edge cases around empty, missing, or out-of-range input. Skip tests whose only assertion is that a component rendered the string it was handed, that a prop reached a child, or that a constant still equals itself.
